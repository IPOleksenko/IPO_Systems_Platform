# Виртуальная файловая система и IPO_FS

Хранение данных в IPO_OS организовано через слой виртуальной файловой системы (VFS) поверх **IPO_FS** — собственной 64-битной файловой системы на непрерывных блочных цепочках (экстентах).

### Принцип работы экстентов (Extents)
В отличие от классических систем с многоуровневыми косвенными блоками указателей, требующими множества позиционирований головки диска, `IPO_FS` использует непрерывные диапазоны секторов — **экстенты**:
```c
struct ipo_extent {
    uint64_t logical_block;   /* Логический блок внутри файла */
    uint64_t physical_block;  /* Начальный физический сектор в разделе */
    uint32_t block_count;     /* Число непрерывных 512-байтных блоков */
    uint32_t flags;
};
```
- Первые **4 экстента** размещены непосредственно внутри 128-байтного дескриптора inode.
- Если файлу требуется более 4 несмежных фрагментов, поле `next_extent_node` указывает на блок `ipo_extent_node`, содержащий цепочку из **20 дополнительных экстентов**.

## 📂 Записи каталога (`ipo_dir_entry`)

Каталоги в `IPO_FS` хранятся как файлы, содержимое которых состоит из массива записей переменной длины:

```c
struct ipo_dir_entry {
    uint32_t inode;       /* Номер целевого дескриптора inode */
    uint32_t rec_len;     /* Полная длина записи в байтах */
    uint32_t name_len;    /* Длина имени файла (до 64 байт) */
    uint8_t  type;        /* 0x1 = Каталог, 0x2 = Обычный файл */
    uint8_t  reserved[3];
    /* Далее следует имя файла char name[] */
};
```

## 🧱 Уровень блочных устройств (`block_dev.c`) и таблиц разделов (`partition.c`)

Под файловой системой `IPO_FS` расположен универсальный стек блочного хранения с динамическими структурами данных (без фиксированных ограничений длины массивов):
- **Блочные устройства (`block_device_t`):** Каждый физический или виртуальный накопитель (`ata0`, `ata1` и т. д.) регистрируется через `block_dev_register()` с динамическим именем `char *name`, размером сектора, общим числом секторов и колбэками `read_sectors()`, `write_sectors()` и `flush()`.
- **Сканер разделов MBR и GPT (`partition_scan`):** Автоматически распознаёт классическую разметку **MBR** (`0x55AA`, до 4 первичных разделов, тип `0x83` для `IPO_FS`) и заголовки **GPT** (`"EFI PART"` в LBA 1), сохраняя найденные разделы в динамический массив `partition_table_t`.

## 🔗 Персистентный многодисковый пул хранения (`storage_pool.c`) и журнал WAL

Подсистема **Storage Pool** (`src/kernel/storage/storage_pool.c`, `src/include/storage/storage_pool.h`) объединяет один или несколько физических дисков (`ata0`, `ata1`, ...) в единое непрерывное логическое пространство блоков (**Spanned JBOD Volume**) с транзакционной защитой метаданных:

### 1. Разметка метаданных пула на диске (LBA 2030–2039)
Метаданные пула располагаются в зарезервированной области перед началом раздела `IPO_FS` (`LBA 2048`):

| Секторы LBA | Размер | Структура | Назначение |
| :--- | :--- | :--- | :--- |
| **`LBA 2030`** | 512 Б (1 сектор) | `storage_pool_raw_sb_t` | **Первичный суперблок пула** (`magic = 0x504F4F4C` `'POOL'`, версия 2, контрольная сумма CRC32, гибкий массив дисков `members[]`) |
| **`LBA 2031–2038`** | 4 КБ (8 секторов) | `storage_raw_disk_tx_entry_t[64]` | **Журнал предзаписи транзакций (WAL)**: 64 записи по 64 байта (`magic = 0x54584E4C` `'TXNL'`, фазы `INIT` → `PENDING` → `COMMITTED`) |
| **`LBA 2039`** | 512 Б (1 сектор) | `storage_pool_raw_sb_t` | **Резервный суперблок пула (Backup Superblock)** для автоматического восстановления при повреждении LBA 2030 |

<SharedStruct id="storage_pool_raw_sb" lang="ru" />

### 2. Журнал транзакций Write-Ahead Logging (WAL) и автовосстановление
Перед любой записью блоков через `storage_pool_write_blocks()` подсистема фиксирует транзакцию в кольцевом журнале WAL (LBA 2031–2038):
1. Создаётся запись `storage_raw_disk_tx_entry_t` с порядковым номером `seq_id`, временем начала, целевым диапазоном `start_lba` / `sector_count`, индексом диска-участника и контрольной суммой CRC32 в статусе `STORAGE_TX_PENDING`.
2. Выполняется физическая запись данных на целевой накопитель пула.
3. Запись в журнале переводится в статус `STORAGE_TX_COMMITTED`, обновляется счётчик `generation` суперблока и вызывается `flush()`.
4. При загрузке ОС или вызове `storage_pool_recover()` ядро проверяет CRC32 первичного суперблока (при ошибке переключается на резервный в LBA 2039) и сканирует журнал WAL, автоматически откатывая незавершённые (`PENDING`) транзакции.

<SharedStruct id="storage_raw_disk_tx_entry" lang="ru" />

### 3. Управление пулом из командной оболочки (`storage`) и syscall `statvfs`
Системный вызов `IPO_SYSCALL_FS_STATVFS` (`0x1064`) возвращает в пространство пользователя полную статистику ёмкости смонтированного тома, а встроенная команда терминала `storage` позволяет управлять пулом на лету:
```bash
storage status                  # Статус пула, UUID, поколение и состояние WAL
storage list                    # Список всех блочных устройств и участников пула
storage usage                   # Детальная сводка занятого и свободного места IPO_FS
storage check                   # Проверка целостности CRC32 суперблоков и журнала WAL
storage create [uuid] [dev]    # Создание и сохранение персистентного пула на диске
storage add <dev>                # Динамическое расширение пула новым накопителем
storage recover                 # Восстановление суперблока из резервной копии и откат WAL
storage save                    # Принудительная синхронизация суперблоков на диск
```
