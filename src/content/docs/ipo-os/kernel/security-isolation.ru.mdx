# Изоляция и защита памяти

В IPO_OS реализована надёжная модель стабильности и изоляции для аппаратной платформы x86. Работая в плоском 32-битном защищённом режиме, система обеспечивает устойчивость ядра и изоляцию задач через **секционирование памяти процессов**, **подкачку данных приложений (`process_map_app`)**, **изоляцию экранных буферов VRAM** и **двухуровневую обработку аппаратных исключений**.

---

## 🛡️ Архитектурные основы изоляции

```
┌──────────────────────────────────────────────────────────────────┐
│                   Исполнение активного процесса                  │
│   • Код загружен по адресу 0x800000 (PROCESS_HEAP_START)         │
│   • Динамический стек в kmalloc (256 КБ начальный размер)        │
│   • Буфер аргументов по адресу 0xBFF000                          │
└────────────────────────────────┬─────────────────────────────────┘
                                 │ переключение process_map_app()
┌────────────────────────────────▼─────────────────────────────────┐
│                  Хранилище фоновых приложений                    │
│   • Буферы binary_storage в динамической памяти ядра             │
│   • Сохранение изменённых секций .data и .bss при переключении   │
│   • Сегменты кучи процессов: 0x08000000 + (pid-1)*0x04000000     │
└──────────────────────────────────────────────────────────────────┘
                                 │
┌────────────────────────────────▼─────────────────────────────────┐
│                     Защита исполнительного ядра                  │
│   • Код ядра в 0x10000, стек на 5 МБ в 0x500000                  │
│   • Выделенный пул kmalloc на 16 МБ в 0x1000000                  │
│   • Двухуровневый cpu_exception_handler: изоляция сбоев          │
└──────────────────────────────────────────────────────────────────┘
```

## 🧠 1. Секционирование динамической памяти процессов

Для исключения взаимного повреждения областей памяти:
1. **Куча ядра:** Расположена по адресу `0x1000000` (16 МБ) с фиксированной ёмкостью 16 МБ.
2. **Кучи процессов (`sbrk`):** Динамические пользовательские аллокации разделены на непересекающиеся сегменты по 64 МБ:
   `Базовый адрес = 0x08000000 + (PID - 1) * 0x04000000`
   Максимальная ёмкость сверяется с объёмом физической RAM, считанным из `0x8FF0`.

---

## 🔄 2. Отображение и подкачка памяти (`process_map_app`)

При кооперативной многозадачности в пакетном режиме:
- При переключении процесса функция `process_map_app(process_t *proc)` сохраняет изменённые сегменты данных `.data` и `.bss` текущего приложения в его буфер `binary_storage`.
- Данные входящего процесса копируются обратно в `0x800000`.
- Это гарантирует, что одновременно запущенные программы не перезаписывают глобальные переменные друг друга.

---

## 📺 3. Изоляция экранных буферов VRAM и рабочих пространств

Каждый процесс в пакетном режиме обладает независимой виртуальной консолью:
- **`text_vram_backup`:** Буфер текстового режима 80x25 (4000 байт).
- **Буферы истории:** Верхний и нижний буферы прокрутки (`scroll_top_buffer`, `scroll_bottom_buffer`).
- **Состояние курсора:** Координаты и флаг видимости курсора.
При смене активного процесса физический видеопамять `0xB8000` мгновенно обновляется без артефактов.

---

## 🚨 4. Двухуровневое восстановление после сбоев (Исключения ЦП)

Исключения процессора (0–31: деление на ноль, недопустимая инструкция, GPF) перехватываются функцией `cpu_exception_handler(uint32_t *frame)` в `src/kernel/syscall/syscall.c`:

1. **Изоляция сбоя пользовательского процесса:**
   Если сбой произошёл во время работы приложения (`proc != NULL`), ядро выводит диагностику (вектор, имя ошибки, адрес `EIP`) и подменяет адрес возврата:
   ```c
   frame[9] = (uint32_t)process_crash_exit;
   ```
   По инструкции `iretd` процессор возвращается в `process_crash_exit`, корректно освобождает ресурсы упавшего процесса и возвращает управление в командную строку ядра без паники ОС!
2. **Граница паники ядра:**
   Если сбой произошёл внутри критического кода ядра (`proc == NULL`), система выводит сообщение `KERNEL PANIC` в VGA и COM1, после чего останавливается командой `cli; hlt`.

---

## 🔍 5. Валидация параметров системных вызовов

Все указатели буферов и аргументы, передаваемые через массив `ECX` (`const uint32_t *argv`), проверяются диспетчером системных вызовов:
- Проверка нулевых указателей.
- Проверка размера буферов и целочисленного переполнения.
- Ошибочные параметры возвращают отрицательные коды ошибок (`-IPO_ERR_INVALID_PARAM` или `-IPO_ERR_BAD_ADDRESS`).
