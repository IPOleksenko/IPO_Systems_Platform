# Формат бинарных файлов и карта памяти

В IPO_OS используется чистая и детерминированная модель исполнения. Вместо динамических компоновщиков или таблиц релокаций приложения собираются как **чистые плоские бинарные образы** (raw flat binaries), скомпонованные для исполнения по адресу `0x00800000` (`PROCESS_HEAP_START`, 8 МБ).

---

## 🗺️ Карта памяти процесса

Каждое приложение в IPO_OS выполняется в плоском 32-битном адресном пространстве:

```
+----------------------------------------------------+ Верхняя граница RAM
| Секционированные кучи (0x08000000 + (pid-1)*64M)   |
+----------------------------------------------------+ 0x08000000 (128 МБ)
| Динамическая куча ядра (kmalloc, 16 МБ)            |
|   • Стеки процессов (256 КБ через setup_stack)     |
|   • Массив аргументов процесса (argv) и окружение  |
+----------------------------------------------------+ 0x01000000 (16 МБ)
| .bss (Неинициализированные глобальные переменные)   |
+----------------------------------------------------+
| .data (Инициализированные переменные)              |
+----------------------------------------------------+
| .rodata (Строковые константы и литералы)           |
+----------------------------------------------------+
| .text (Исполняемый код, точка входа _start)        |
+----------------------------------------------------+ 0x00800000 (8 МБ)
| Память ядра (Код в 0x10000, стек ядра в 0x500000)  |
| Байт объёма RAM сохранён по адресу 0x8FF0          |
+----------------------------------------------------+ 0x00000000
```

## 📦 Структура плоского бинарного файла

Плоский бинарный файл (`.bin`) не содержит заголовков ELF или таблиц секций. Он представляет собой непрерывный поток машинных инструкций и байтов данных:

```
Смещение в .bin     Секция           Описание
0x00000000          .entry / .text   Инструкция перехода (jmp main)
+0x00000020          .text            Скомпилированные функции
...                  .rodata          Константы и строки
...                  .data            Инициализированные переменные
...                  .bss             Включена в виде заполнения нулями
```

### Преимущества плоского бинарного формата:
1. **Мгновенная загрузка:** Функция `exec` ядра считывает файл с диска напрямую в память по адресу `0x00800000`.
2. **Детерминированный запуск:** Исполнение начинается сразу же переходом на `0x00800000` без парсинга символов.
3. **Простота:** Исключает сложный код парсинга ELF на ранних стадиях ОС.

## ⚙️ Скрипт компоновщика (`applications/app.ld`)

Приложения компонуются стандартным скриптом `applications/app.ld`:

```c
ENTRY(_start)

SECTIONS
{
    . = 0x800000;

    .text : ALIGN(4) {
        *(.entry)
        *(.text.startup)
        *(.text.main)
        *(.text*)
    }

    .rodata : ALIGN(4) { *(.rodata*) }
    .data   : ALIGN(4) { *(.data*) }
    .bss    : ALIGN(4) {
        __bss_start = .;
        *(COMMON)
        *(.bss*)
        __bss_end = .;
    }
    _end = .;
}
```

Точка входа `applications/entry.s`:
```asm
.global _start
.extern main

.section .entry, "ax"
_start:
    jmp main
```

## ⚠️ Требование к секции `.bss`

В обычных файлах Linux ELF неинициализированные переменные (`.bss`) не занимают места на диске, так как загрузчик ELF обнуляет их при старте.

Однако в чистом плоском бинарнике отсутствие `.bss` приведёт к смещению и повреждению последующих данных. Для плоских файлов IPO_OS утилита `objcopy` инструктируется принудительно включить секцию `.bss` в виде нулевых байтов:

```bash
objcopy --set-section-flags .bss=alloc,load,contents \
        -j .text -j .rodata -j .data -j .bss \
        -O binary app.elf app.bin
```
