# Архітектура бінарних форматів, завантажувач та модель пам'яті

В операційній системі IPO_OS реалізовано гнучку та надійну підсистему виконання програм, ключовим компонентом якої є **Універсальний завантажувач виконуваних файлів** (`exec_load()` у `src/kernel/core/process.c:3469`). Працюючи разом із `process_spawn()`, `kmod_load_file()` та користувацьким лінкером `dlopen()`, ядро підтримує завантаження як ELF32 з автоматичною DWARF-рефлексією типів, так і плоских бінарників і скриптів із шебангом, гарантуючи захисну верифікацію текстових файлів та швидке кооперативне перемикання пам'яті процесів.

---

## 🗺️ Карта пам'яті процесів та організація адресного простору

Кожен користувацький застосунок в IPO_OS виконується у 32-бітному плоскому адресному просторі:

```
+-------------------------------------------------------------+ Верх пам'яті RAM
| Ізольовані динамічні купи (0x08000000 + slot*stride)        | Виділення через sbrk()
+-------------------------------------------------------------+ 0x08000000 (128 МБ)
| Пул сторінок фреймів PMM (memory_map_alloc) / Купа при <128M|
+-------------------------------------------------------------+ 0x05000000 (80 МБ)
| Динамічна купа ядра (kmalloc, місткість 64 МБ)              |
|   • Стеки процесів (по 256 КБ кожен, setup_stack)           |
|   • Буфери образів процесів у пам'яті ядра (binary_storage) |
|   • Масиви аргументів (argv) та змінні оточення             |
+-------------------------------------------------------------+ 0x01000000 (16 МБ)
| Активна область виконання застосунку (з binary_storage)     |
|   • .bss (Неініціалізовані глобальні змінні)                |
|   • .data (Ініціалізовані глобальні змінні)                 |
|   • .rodata (Рядкові літерали та константи)                 |
|   • .text (Виконуваний машинний код, точка входу 0x00800000)|
+-------------------------------------------------------------+ 0x00800000 (8 МБ)
| Простір ядра (Код з 0x10000, стек ядра на 0x500000)         |
| Карта E820 на 0x6000, заголовок детекції RAM на 0x8FE0      |
+-------------------------------------------------------------+ 0x00000000
```

## 📦 Підтримувані виконувані та динамічні формати

Платформа IPO_OS підтримує 6 форматів виконуваних файлів, модулів та скриптів:
1. **32-бітні виконувані файли ELF (`ET_EXEC`, `EM_386`):** Виконуються через користувацький завантажувач `/applications/elf_loader`, зареєстрований у підсистемі `binfmt` за сигнатурою `\x7fELF`. Завантажувач розбирає `Elf32_Phdr`, сегменти `PT_LOAD`, застосовує релокації `SHT_REL`, обнуляє `.bss`, детектує повернення структур (`is_entry_struct_return`) та сигнатуру типу повернення (`IPOR` `0x524F5049`), реєструючи тип викликом `SYS_SET_RETURN_VALUE` (0x1029).
2. **Плоскі бінарні образи (`.bin`):** Завантажуються ядром напряму через стандартний bare-metal завантажувач `exec_load()` за адресою `0x00800000` (`PROCESS_HEAP_START`, 8 МБ). Виконуються напряму без метаданих, а код виходу повертається через регістр `EAX`.
3. **Динамічний реєстр форматів (`binfmt` та `/autorun`):** Системні виклики `0x10E0` (`IPO_SYSCALL_BINFMT_REGISTER`), `0x10E1` (`IPO_SYSCALL_BINFMT_UNREGISTER`), `0x10E2` (`IPO_SYSCALL_BINFMT_LIST`). Під час завантаження ОС `/autorun` запускає `/applications/binfmt`, який реєструє формати ELF32, Lua, Python, TinyCC та Shell. Утиліта командного рядка `binfmt` дозволяє переглядати та додавати формати під час роботи.
4. **Скрипти з шебангом (`#!`) та тегами заголовків:** Автоматично обробляються підсистемою `binfmt` з глибиною вкладеності до 16 рівнів.
5. **Динамічні модулі ядра (`.kmd`, Ring 0):** Завантажуються через `kmod_load_file()`, містять сигнатуру `'KMOD'`, перевірку версії ABI, контрольну суму CRC32 та бінарний пошук по таблиці символів `ksymtab` (~1560 символів).
6. **Розділювані бібліотеки та об'єктні файли (`.so`, `.o`):** Динамічне завантаження в користувацькому просторі через `dlopen()`, `dlsym()`, `dlclose()` (`IPO_OS_Software/lib/libc/dlfcn.c`).

## ⚡ Динамічне виділення у вільне місце та перемикання контексту без копіювання

В IPO_OS багатозадачні процеси не копіюються по черзі у єдине статичне вікно. Замість цього кожен процес розміщується в динамічно виділеному вільному блоці пам'яті:

1. **Аллокатор першого відповідного блоку (`allocate_process_memory`):**
   - Ядро виконує пошук у таблиці `allocated_blocks` відповідного вільного блоку (`pid == 0`) потрібного розміру. Якщо знайдений блок більший за потрібний, він розбивається (`split`), залишаючи залишок вільним.
   - Якщо вільний блок відсутній, пам'ять виділяється у вільному просторі в кінці пулу (`PROCESS_HEAP_START + global_process_heap_used`).
2. **Виконання безпосередньо на місці (In-Place):**
   - Машинний код завантажується напряму у виділений блок пам'яті (`proc->binary_base = mem`).
   - Точка входу встановлюється на адресу виділеного блоку (`proc->entry_point = (uint32_t)mem`), при цьому `proc->binary_storage = NULL` і `proc->code_mapped = true`.
3. **Перемикання контексту без копіювання (`process_switch_context`):**
   - Перемикання процесів зберігає та відновлює регістри процесора та стек (`%esp`, `%ebp`, `%ebx`, `%esi`, `%edi`, `eflags`) без накладних витрат на копіювання образів.
   - Функція `process_map_app(proc)` фіксує вказівник `currently_mapped_app` для віконного менеджера та драйверів без переміщення пам'яті.
4. **Звільнення та об'єднання вільних блоків:**
   - Після завершення процесу `free_process_memory()` позначає блок як вільний (`pid = 0`).
   - Функція `coalesce_free_blocks()` автоматично об'єднує суміжні вільні блоки у єдині безперервні сегменти.

## 📈 Ізольовані динамічні купи процесів (`process_heap_init`)

- Пам'ять, що виділяється через `malloc()` та `sbrk()`, повністю ізольована для кожного процесу.
- Базовий адрес починається з `0x08000000` (або `0x05000000` при малому обсязі RAM).
- Динамічний крок (stride) масштабується залежно від загального обсягу RAM (256 МБ за замовчуванням, мінімум 32 МБ).
- Створюється з **0 виділених байтів** і зростає за потребою при викликах `sbrk()`.
- Миттєво повертається системі після завершення процесу.

---

## 🎯 Типізований результат процесів (`process_trampoline`)

- Виклик точки входу відбувається через функцію ядра `process_trampoline()`.
- Якщо функція повертає структуру (`is_entry_struct_return`), ядро виділяє буфер зі значеннями `0xDD` і передає його як прихований вказівник.
- Після повернення з `main()` результат серіалізується у `proc->return_val` відповідно до сигнатури DWARF (структури, `String`, `char*`, `float`, `double`, `int64`, `bool`, `int`).
- Результат доступний у командній оболонці та передається через конвеєри (пайпи).
